# x402 acceptance-record checker — independent implementation, run report

Second implementation, written independently, of the acceptance-record
conditions from x402-foundation/tsc#4 (2026-10-04) — nonlinearity's condition
table — plus the key-handling rule at draft-krausz-verification-state-03
§5.4.2 (`key_unresolved` vs `signature_invalid`, with a relying-party
completeness input).

Stdlib only. Ed25519 verification (`ed25519_verify.py`) is a from-scratch
RFC 8032 implementation, self-tested against real signatures generated by
the `cryptography` package (4 message lengths, valid + tampered cases)
before being used here.

Vectors: `examples/acceptance-record-cold/vectors.json` from
[babyblueviper1/preaction-governance-conformance](https://github.com/babyblueviper1/preaction-governance-conformance)
at commit `37fdb856d8fef1c410e69bbd81070da67dd945d8` (`37fdb85`), 46 vectors,
sha256 `464ee7933a17c3ab52db32b93ac21f555a026781f4a8a132b91977eb4fb02882` —
fetched and verified by `run_vectors.py` before every run.

## Result: 46/46 agree (2026-10-13)

Measured at checker commit `05dff1e` and again after each later change (the
disposition fix, then the `ed25519_verify` and canonical-base64url hardening
described below); every time 46/46. Two comparisons exist and they are not
equally strict:

| Comparison | Compares | 46 vectors |
|---|---|---|
| `python3 run_vectors.py` | `result`, `conditions` (as a set), `disposition` when the vector pins one | 46/46 |
| `tests/` (`AllVectors`, upstream runner's definition) | the above **plus every other expected member**: `key_step`, `policy_refusal` | 46/46 |

`run_vectors.py` does **not** compare `key_step` or `policy_refusal`, both of
which the vectors pin; a checker that omitted them would still pass it. The
tests would not. The full suite is 28 tests (`python3 -m unittest discover -s
tests`), all passing.

## History: 22/25, then 23/46, then 46/46

**Original build (`b06ca87`) at upstream `646588c`: 22/25** on every field a
vector pins. Three disagreements, reducing to two reading differences:

1. *Is a failed signature its own result token?* This implementation returned
   `signature_invalid` as a sixth token (exit 2), a peer of `key_unresolved`.
   The vectors (and the upstream README's "Evaluation order", stated
   2026-10-11) have it as `malformed` with `conditions: ["signature_invalid"]`
   (exit 1) and a `key_step` member. 2 of the 3 disagreements.
2. *What is an ill-typed `*_sha256` member?* This implementation treated any
   non-empty string as well-typed, so `"not-hex"` produced a digest mismatch.
   The vectors, and upstream's README, say well-typed means exactly 64
   lowercase hex characters, with the mismatch suppressed. 1 of the 3.

At that point the report said no behavior had been changed after seeing
where the checker disagreed. **That was true of that run and is not true of
the checker now**: both readings were then changed to follow the vectors, in
the open, in the commits below.

**Original checker against the 46-vector file: 23/46** under the strict
comparison (result, conditions, and every other expected member), measured
2026-10-13 before any fix. The 23 that disagreed: 5 of the original 25 (the 3
above, plus a missing `key_step` on `acc-key-unresolved` and
`acc-key-unresolved-declared-complete`, which `run_vectors.py` does not
compare), both vectors of the `a747e46` pair, and 16 of the 19 vectors added
after that (timestamps, header, version, base64url, small-order keys,
`trust_material_complete`, payload order).

**`05dff1e`: 46/46.** Seven fixes, in this order, each with a test written and
run failing first (`tests/test_acceptance_conformance.py`, one class per fix):

1. **Small-order key / `R`.** A trust-material key that is one of the 8
   small-order points (identity included) is `key_unresolved`, with
   `policy_refusal` if declared complete; a signature whose `R` is small-order
   is `signature_invalid`. Under such a key one signature verifies every
   message, so an acceptance under it binds nobody. At `05dff1e` the refusal
   lived only in `checker.py`; see "After `cfc6eeb`" below for `verify()`.
2. **Strict base64url without padding** (RFC 7515 §2): alphabet and length are
   checked, because the stdlib decoder drops stray characters and accepts `=`.
   (Canonical trailing bits were added later; see below.)
3. **`acceptance_version`** is required and exactly `acceptance-record-v0`;
   absent, not a string, or another value is `acceptance_member_invalid`.
4. **`signature_invalid` result model.** `malformed` with that single
   condition (exit 1); `key_step` is reported on both key-step outcomes; the
   payload is parsed only after the key step, so a non-object payload under a
   bad signature is `signature_invalid`; `trust_material_complete` counts only
   as JSON `true`.
5. **Protected header.** `alg` must be `EdDSA` and `kid` a string, found before
   the key step (no usable kid is not `key_unresolved`). Folded into fix 4's
   edit because both rewrite the same lines.
6. **Timestamps** are exactly `YYYY-MM-DDTHH:MM:SS.mmmZ`; any other spelling,
   including an offset naming the same instant, is ill-typed.
7. **Type-check suppression.** `*_sha256` members are 64 lowercase hex; an
   ill-typed member raises `acceptance_member_invalid` only, and the record
   digest is not compared over a record with an ill-typed member.

**After `05dff1e`: `disposition` is null on every `malformed` result.** The
original build reported the signed disposition whenever it parsed (a record
with a good `disposition: "accepted"` and a terms mismatch reported
`accepted`). The 37fdb85 README says it is reported only with `verified` and
`unknown`, null on `malformed` and `key_unresolved`, and `not_responded` on
`no_record`. No vector pins this, so it did not move the 46/46; it was
changed to match the README and is covered by tests written first (20
failures before, 0 after).

**After `cfc6eeb`: `verify()` is safe standalone, and base64url is canonical.**
Neither moved the 46/46 (no vector pins either); both have tests written first
(24 failures before, 0 after).

- `ed25519_verify.verify()` returns `False` for a small-order public key or a
  small-order `R` (all 8 small-order points tested, as key and as `R`), where
  before it returned `True` for the identity key with `R` = identity, `S` = 0
  (and for a small-order `R` under a real key). It still raises
  `Ed25519VerifyError` for structurally malformed input, and genuine signatures
  still verify. `checker.py` keeps its own split: a small-order key is
  `key_unresolved`, a small-order `R` is `signature_invalid`; it now calls a
  public `is_small_order()` in `ed25519_verify.py` instead of private helpers.
- A base64url string with non-zero unused trailing bits (a second spelling of
  the same bytes, which the stdlib decoder accepts) is rejected: the decoded
  bytes must re-encode to exactly the input. For the acceptance members that is
  `acceptance_member_invalid` before the key step; for a trust-material `x` it
  is an unusable key, so `key_unresolved`. Before, a record with a re-spelled
  signature verified.

## Sentence-8 choices

| Input | This checker |
|---|---|
| `trust_material_complete` | A declaration only as JSON `true`. `false`, omitted, `"true"` and `1` are all "not complete"; no `policy_refusal` is emitted (the vector `acc-complete-not-boolean` pins `policy_refusal: null`). A plain `false` used to emit `policy_refusal: false`; it now emits nothing. |
| Same `kid` twice in the trust material | The first Ed25519 entry for that kid decides. If it is unusable (bad base64url, not 32 bytes, small-order) the kid is `key_unresolved`; a later duplicate does not rescue it. The original build skipped unusable entries and tried the next, so this is a behavior change, made because small-order rejection with skip-and-continue would let a good second entry override a bad first one. Covered by `test_duplicate_kid_first_entry_decides` (both orders). |

Neither is refused as an input error. A relying party that wants either case
refused should do so before calling the checker.

## Decisions no vector pins

Recorded because they are this checker's reading, not the corpus's:

- A payload that is not valid JSON (not only one that is not an object) is
  found after the key step, so under a bad signature the result is
  `signature_invalid`. Only the base64url encoding and the protected header
  are checked before it.
- The first-entry-decides rule above, for the unusable-first-entry case.
- Non-canonical base64url (non-zero trailing bits) is rejected, which is
  stricter than the sentence-2 wording alone requires.

## Independence

The original build (`b06ca87`) was written from the specification text only;
the reference's `tools/acceptance_record_check.py` and `tools/_ed25519.py` were
never opened, and its `build_vectors.py` and `run_vectors.py` were not read.
Changes from `05dff1e` on were made after seeing the disagreements, from the
46 vectors and the upstream `examples/acceptance-record-cold/README.md` at
`37fdb85`; `tools/` was still not opened. The vector builder and runner
(`build_vectors.py`, `run_vectors.py`) were read separately, while
contributing two vectors to that repo (`a747e46`), before `05dff1e`. Treat
the current checker as an implementation corrected against the corpus, not as
an independent first-pass reading.

## Reproduce

```sh
python3 run_vectors.py                                  # fetches and verifies the pinned vectors
ACCEPTANCE_VECTORS=/path/to/vectors.json \
  python3 -m unittest discover -s tests                 # strict comparison and per-fix tests
```
