# x402 acceptance-record checker — independent implementation, run report

Second, from-scratch implementation of the acceptance-record conditions from
x402-foundation/tsc#4 (2026-10-04) — nonlinearity's condition table — plus
the key-handling rule at draft-krausz-verification-state-03 §5.4.2
(`key_unresolved` vs `signature_invalid`, with a relying-party completeness
input). Written against the specification only. `tools/acceptance_record_check.py`,
`tools/_ed25519.py`, `build_vectors.py`, and that source repo's own
`run_vectors.py` were never opened while writing this.

Stdlib only. Ed25519 verification (`ed25519_verify.py`) is a from-scratch
RFC 8032 implementation, self-tested against real signatures generated by
the `cryptography` package (4 message lengths, valid + tampered cases)
before being used here.

Vectors: `examples/acceptance-record-cold/vectors.json` from
[babyblueviper1/preaction-governance-conformance](https://github.com/babyblueviper1/preaction-governance-conformance)
at commit `646588cbab5e3cfe0824af6bb83ee1779f0f67ee`, sha256
`c7f5513a6292a8cb7a8049b30113ed9bb786843717c62e7f806c73843c04e7e0` — fetched
and verified by `run_vectors.py` before every run.

## Result: 22/25 agree on every field the vector pins; 3 genuinely disagree

A vector pins `result` and `conditions` always, and `disposition` only for
`verified`, `no_record`, and `unknown` results — it is simply absent as a
key for every `malformed`/`key_unresolved`-family result. Comparing only
against what each vector actually asserts: **22 of 25 agree exactly**. The
other 3 reduce to **two confirmed reading differences** (both
implementations pin something on the same field, and the values differ) —
plus a broader, genuinely open question the vectors never assert either way
in the first place, documented below because it's real and worth stating
even though it isn't one of the 3 counted disagreements.

No expectation, reading, or behavior in `checker.py` was changed after
seeing where it disagreed with the vectors.

### Reading difference 1 — is a failed signature its own result token, or a `malformed` condition? (2 of the 3 disagreements)

Source sentence this implementation read as controlling: the spec's
"Result tokens" table lists five rows — `verified`, `unknown`,
`key_unresolved`, `no_record`, `malformed` — and does not list
`signature_invalid` as a sixth. At the time of writing the checker, with no
vector yet examined, this was read as the table simply being non-exhaustive
for a case none of the 25 vectors happened to exercise, since the
surrounding prose ("Not malformed, and not a failed signature" — §5.4.2(a),
describing `key_unresolved`) explicitly contrasts `key_unresolved` against
a failed signature, which reads naturally as implying the failed-signature
case is some other, parallel, named thing.

What the vectors imply: `acc-signature-invalid` and
`acc-signature-invalid-declared-complete` both pin `result: "malformed"`,
`conditions: ["signature_invalid"]` (plus a `key_step: "signature_invalid"`
field present on these and on the `key_unresolved` vectors, used to record
which key-step sub-case occurred independently of how it surfaces in
`result`). Under this reading, only `key_unresolved` is special-cased with
its own token — specifically because the check never ran at all, so there
is genuinely nothing to report as a finding — while a failed signature is a
definite, confirmed finding and belongs in the general `malformed` bucket
alongside every other confirmed finding, with `key_step` carrying the extra
detail of which step produced it.

**Reading A (this implementation)**: `key_unresolved` and `signature_invalid`
are peers — both terminal, both exit code 2, neither one a `malformed`
finding, because in both cases the key step did not produce a trustworthy
basis for proceeding, "basis for proceeding" treated as the thing that
decides whether something is reportable as a finding at all.

**Reading B (the vectors)**: only `key_unresolved` is a peer of `verified`/
`no_record`/`unknown`; `signature_invalid` is one more `malformed` finding
like any of the six/seven report-all conditions, distinguished from them
only by the extra `key_step` field, not by its place in `result`.

Neither reading contradicts the literal "Result tokens" table — it has five
rows under both readings, since Reading B's `signature_invalid` never
claims to be a sixth row of that table, it is a member of `conditions`
under the existing `malformed` row.

### Reading difference 2 — what counts as an "ill-typed" `*_sha256` member? (1 of the 3 disagreements)

Source sentence: "an ill-typed member raises `acceptance_member_invalid`
only, not the mismatch that depends on it" (the report-all /
type-check-suppression rule).

`acc-illtyped-digest-suppresses-mismatch` supplies `terms_sha256: "not-hex"`
— a non-empty, well-formed JSON string, but not 64 hex characters.

**Reading A (this implementation)**: "ill-typed" is a JSON-type question —
a string-typed field holding any non-empty string is well-typed, whatever
its content. `"not-hex"` therefore passed the type check and was compared
literally against the real digest, producing
`acceptance_terms_digest_mismatch`.

**Reading B (the vector)**: expects `acceptance_member_invalid`, with the
mismatch condition suppressed entirely — implying "ill-typed" for a
`*_sha256`-named member means "not a value usable as a sha256 digest" (hex
alphabet, 64 characters), a content/shape check folded into what "typed"
means for this specific class of field, not merely its JSON type.

Both readings are internally consistent with the word "ill-typed" alone;
the text does not say which scope — JSON type, or digest-shaped-string — the
word is meant to cover.

### An open question the vectors never assert either way — does a non-clean result ever report `disposition`?

Not one of the 3 counted disagreements (no vector pins a `disposition`
value here for either implementation to agree or disagree with), but worth
recording: this implementation always includes a `disposition` field,
populated from the payload whenever the payload's `disposition` member
parses as one of `accepted`/`rejected`/`disputed`, regardless of what else
is wrong with the record — e.g. a record with a correct, parseable
`disposition: "accepted"` but a terms-digest mismatch still reports
`disposition: "accepted"` here. The 13 vectors with a `malformed` or
`key_unresolved`-family result simply never include a `disposition` key at
all, for either a correct or incorrect value — the vectors are silent on
whether that silence means "no opinion, fill in what you can determine" or
"this field has no meaning once the result isn't clean." Because no vector
asserts a specific value here, this is not counted as one of the 3
disagreements above, but it is a real difference in what the two
implementations would emit for the same malformed input.

## Full results

Reproduce with `python3 run_vectors.py` (fetches and verifies the vectors
automatically). Full table and disagreement detail are printed to stdout.

Disagreements (3): `acc-illtyped-digest-suppresses-mismatch`,
`acc-signature-invalid`, `acc-signature-invalid-declared-complete`.

All other 22 vectors agree exactly on every field they pin.
