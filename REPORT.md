# x402 acceptance-record checker — independent implementation, run report

Second, from-scratch implementation of the acceptance-record conditions from
x402-foundation/tsc#4 (2026-10-04), written against the specification only
(the condition names/semantics given directly, plus the public prose spec at
`x402run/pgc/examples/acceptance-record-cold/README.md`, which documents the
GitHub issue — not the checker's code). `tools/acceptance_record_check.py`,
`tools/_ed25519.py`, `build_vectors.py`, and `run_vectors.py` in that clone
were never opened while writing this.

Stdlib only. Ed25519 verification (`ed25519_verify.py`) is a from-scratch
RFC 8032 implementation, self-tested against real signatures generated by
the `cryptography` package (4 message lengths, valid + tampered cases) before
being used here.

Vectors file: `~/x402run/pgc/examples/acceptance-record-cold/vectors.json`,
sha256 `c7f5513a6292a8cb7a8049b30113ed9bb786843717c62e7f806c73843c04e7e0` —
verified by `run_vectors.py` before running (aborts on mismatch).

## Result: 10/25 agree, 15 disagree

All 15 disagreements reduce to exactly **three** systemic reading
differences — not 15 independent bugs. None of them were fixed; the checker
was not changed after seeing these results.

### Disagreement 1 — does a non-clean result ever report a `disposition`? (13 vectors)

The reference vectors never include a `disposition` key at all once the
result is `malformed` or the key step didn't cleanly resolve-and-verify
(`key_unresolved`, and the `signature_invalid`-as-`malformed` cases — see
Disagreement 2). My checker always includes `disposition` as a field,
computed from the payload when the payload's `disposition` member is
syntactically one of `accepted`/`rejected`/`disputed`, regardless of what
else is wrong with the record — e.g. a record with a correct, parseable
`disposition: "accepted"` but a terms-digest mismatch still reports
`disposition: "accepted"` in my output, where the reference vectors simply
omit the field.

Reading taken here: `disposition` is a payload member like any other; its
correctness is independent of the OTHER members' correctness, so a
malformed record can still truthfully report what it claims its own
disposition is, same way an otherwise-invalid document can still have a
syntactically valid `name` field. The relying party gets the fact plus the
warning (`conditions`), and decides what to do with a claimed-but-untrusted
disposition.

Reading implied by the vectors: once a record is not cleanly `verified`,
its `disposition` is not reported at all, trusted or not. This reads
`disposition` as meaningful only in the context of an overall-good record —
closer to "don't partially trust a document that failed validation,"
treating disposition less as an independent field and more as an output
that is only produced once the whole record has been accepted as
well-formed and genuinely signed.

Affected vectors: `acc-confirming-party-absent`, `acc-confirming-party-empty`,
`acc-signer-is-issuer-same-kid`, `acc-signer-is-issuer-reused-key-new-kid`,
`acc-signer-is-issuer-same-party`, `acc-terms-digest-mismatch`,
`acc-outcome-digest-mismatch`, `acc-precedes-outcome`,
`acc-report-all-two-mismatches`, `acc-malformed-plus-authority`,
`acc-record-digest-mismatch-replayed`, `acc-record-digest-absent`, and
(jointly with Disagreement 3) `acc-illtyped-digest-suppresses-mismatch`.

### Disagreement 2 — is a failed signature its own result token, or a `malformed` condition? (2 vectors)

The README's "Result tokens" table lists five tokens (`verified`, `unknown`,
`key_unresolved`, `no_record`, `malformed`) and does not list
`signature_invalid` as a row — a detail I read, at the time of designing
the checker, as the table simply being non-exhaustive for a case no vector
happened to exercise. The actual vectors settle this: `acc-signature-invalid`
and `acc-signature-invalid-declared-complete` both expect
`result: "malformed"`, `conditions: ["signature_invalid"]`, plus a separate
`key_step: "signature_invalid"` field the vectors use (on both this case and
the `key_unresolved` vectors) to record which key-step sub-case occurred,
independent of how it surfaces in `result`.

Reading taken here: the key step (RFC/draft-krausz-verification-state-03
§5.4.2) produces one of three OUTCOMES (resolved-and-verified,
key_unresolved, signature_invalid), and the latter two are each their own
terminal result, parallel to each other, both at exit code 2, because
neither one means anything was found to be malformed — the record might be
perfectly well-formed and simply signed by/attributed to the wrong key.
`key_unresolved` and `signature_invalid` are peers under this reading.

Reading implied by the vectors: `key_unresolved` is special-cased as its own
token (per §5.4.2(a)'s explicit "not malformed, and not a failed signature"
language in the README), but `signature_invalid` is NOT given the same
special status — a failed signature is treated as one more thing that can be
wrong with a record, reported the same way any other `conditions` entry is,
via the general `malformed` bucket (exit code 1), with the `key_step` field
carrying the extra detail that this particular malformed finding came from
the key step rather than the report-all member checks. Under this reading,
`key_unresolved` and `signature_invalid` are NOT peers — only
`key_unresolved` gets elevated to a dedicated token, specifically because
(per the README) it is genuinely indeterminate (the check never ran), while
a failed signature is a definite, confirmed finding and therefore belongs
with the other definite findings in `malformed`.

### Disagreement 3 — what counts as an "ill-typed" `*_sha256` member? (1 vector, also exhibits Disagreement 1)

`acc-illtyped-digest-suppresses-mismatch` supplies `terms_sha256: "not-hex"`
— a non-empty JSON string, but not a 64-character hex digest. My checker's
type-check-suppression only verifies JSON type (`isinstance(v, str) and v`),
so `"not-hex"` passes that check, gets compared literally against the real
digest, and is reported as `acceptance_terms_digest_mismatch`. The vector
expects `acceptance_member_invalid` instead — the mismatch condition
suppressed, per the "type-check suppression" rule in the spec, because the
member never qualified as a comparable digest in the first place.

Reading taken here: "ill-typed" means the JSON type is wrong (e.g. a number
or object where a string is required) — a string value, regardless of its
content, is well-typed for a string-typed field.

Reading implied by the vector: "ill-typed" for a `*_sha256` member means
"not a value that is actually usable as a sha256 digest" — i.e. the checker
is expected to validate the value's shape (hex alphabet, 64 characters) as
part of typing it, not just its JSON type, before ever attempting a
mismatch comparison.
